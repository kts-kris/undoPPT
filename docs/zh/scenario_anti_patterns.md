# undoPPT 场景避坑与红线规范

> [English](../en/scenario_anti_patterns.md) | 简体中文

> **版本**：v3.8.0（写于 v3.2.0；在 v3.4、v3.6、v3.7 中扩充）  
> **状态**：正式工程标准  
> **读者**：AI Agent（认知规划器）与评审者

本文规定了 `undoPPT` 支持的 6 个场景原型（第 2 节）以及建立在其上的 12 个企业场景（第 3 节）的严格避坑准则、红线、套话黑名单与修辞质量要求。AI Agent（在编写提示词时）与确定性审计器（`cli.py audit`）都严格遵守这些规则。

---

## 1. 通用红线（所有场景）

无论场景原型是什么，下面这些禁令都适用于整份演示文稿：

### 1.1 禁用的 AI 废话与空洞套话黑名单
下列短语与黑话模式严格禁用。自动语义审计器把它们的出现视为高严重度扣分项：

| 类别 | 禁用的短语 / 模式 | 理由与建议的替代 |
| :--- | :--- | :--- |
| **公式化的 AI 套话** | `不仅是...，更是...`<br>`不仅...而且...`<br>`...是...的必由之路/坚实基石`<br>`为什么/凭什么/怎么做` | 空洞的修辞膨胀。直接陈述事实论断，并交代具体的因果机制。 |
| **抽象的管理黑话** | `打法`、`闭环`、`抓手`、`赋能`、`底层逻辑`<br>`颗粒度`、`盘活`、`破局`、`解构`、`对齐`（没有具体动作时） | 用空洞的词汇掩盖没有实质内容。请用具体动词：`构建`、`降低`、`交付`、`测试`、`重构`、`量化`。 |
| **被动 / 中性标题** | `现状分析`、`系统架构`、`背景介绍`<br>`项目概况`、`思考与探索`、`总结与回顾`<br>`Overview`、`Introduction`、`Architecture` | 每一页的标题都必须是陈述结论或判断的**行动标题**（例如 `痛点：……` 或 `成效：……`）。 |
| **编造的指标与虚假证明** | 凭空捏造带小数的数字、伪造基准测试，或未经验证的故障根因 | 拿不到实证时，不要把数字写成事实：给它一个 `source`，或标 `status: "estimate"`、`"illustrative"`、`"todo"`（页面上分别显示为"估算""示例数据""待核"）。绝不把假设伪装成已验证的数据。 |
| **装饰性杂乱与卡片墙** | 为填满画布堆 8 张以上的卡片；彩虹霓虹渐变；发光卡片效果 | 简洁与结构带来清晰。严格遵守各图元的容量预算（例如 Bento 卡片最多 2~4 张）。 |

## 2. 各场景原型专属红线（6 个场景）

### 2.1 战略规划 (`strategic_planning`)
* **关注点**：高层对齐、取舍、资源分配、三道地平线。
* **禁令与红线**：
  1. **没有边界的愿景不要**：拒绝"打造世界一流的数字化能力"这类含糊的愿景。必须写明具体的战略范围与边界。
  2. **必须有"不做清单"**：真正的战略是关于不做什么。页面必须明确写出取舍与被降级的路径。
  3. **三道地平线治理**：H1（核心业务）、H2（新兴增长）、H3（颠覆性未来）必须写明资源分配比例（如 `70:20:10`）和阶段门禁的退出/日落标准。
  4. **矩阵要精确**：2x2 矩阵必须用可量化或无歧义的标准清楚定义 X 轴与 Y 轴；每个象限要对应一种不同的战略立场。

### 2.2 技术架构 (`tech_architecture`)
* **关注点**：层级解耦、取舍、SLA 指标、演进路线图。
* **禁令与红线**：
  1. **不许对"高可用 / 高性能"空口白话**：严禁"可大规模扩展""超低延迟"这类没有限定的说法。必须给出实测的分位数（`P50/P95/P99 延迟`）、QPS/TPS 阈值与并发上限。
  2. **明确信任边界与故障边界**：架构栈与流程图必须写明外部依赖、调用方向与故障隔离域。
  3. **灾备与回滚门禁**：必须写明降级机制、熔断器与回滚路径。没有回滚方案的方案是不完整的方案。
  4. **取舍维度对等**：对比候选技术时，要把成本（迁移摩擦、认知负担、厂商锁定、基础设施成本）与收益并列。

### 2.3 产品路演 (`product_pitch`)
* **关注点**：客户痛点、自有突破、商业模式、里程碑。
* **禁令与红线**：
  1. **不犯自上而下的宏观谬误**：绝不宣称"全球市场 5000 亿美元，我们只要 1% 就是 50 亿"。TAM/SAM/SOM 必须从目标客户数量与付费意愿自下而上推出。
  2. **用工作流痛点代替泛泛的抱怨**：痛点必须落在具体的工作流摩擦上（如"人工对账每批要花 6 小时"），而不是含糊的抱怨。
  3. **单位经济与飞轮**：必须给出清晰的单位经济（CAC、LTV、回收期或毛利轨迹），而不是对变现一笔带过。
  4. **里程碑交付物**：融资路线图必须把资金的分批使用直接绑定到产品交付物和验证门禁。

### 2.4 个人履历与高管述职 (`personal_resume`)
* **关注点**：岗位画像、核心技术栈、量化的战绩、面向未来的承诺。
* **禁令与红线**：
  1. **不照搬岗位描述**：拒绝"负责支付系统的维护"这类被动的职责陈述。
  2. **强制使用 STAR 方法**：每一项关键成就都要遵循 情境—任务—行动—结果。
  3. **战绩要量化**：结果要用百分比、提速倍数或金额来衡量（如"把 MTTR 降低 45%""每年节省 120 万美元云支出"）。
  4. **划清归属边界**：明确区分个人贡献（负责人）与团队协作（参与者）。不得夸大个人范围。

### 2.5 教育、培训与课件 (`education_training`)
* **关注点**：认知差、误区拆解、循序渐进的概念、练习。
* **禁令与红线**：
  1. **不堆砌教条式术语**：绝不只用抽象的学术黑话定义一个复杂概念，而不把它锚定在学员熟悉的基线上。
  2. **瞄准认知差**：一开始就指出学员常见的盲区与误区。
  3. **必须有反例与最佳实践的对比**：每一条核心原则，都要用具体的"不要这样做"与"应该这样做"的视觉对比来强化。
  4. **可落地的知识检验**：必须包含一道自测题、情景练习或动手挑战，闭合学习回路。

### 2.6 通用企业与资讯类汇报 (`general_informative`)
* **关注点**：背景现状、核心举措、数据成果、执行排期。
* **禁令与红线**：
  1. **不写按时间排列的流水账**：避免事无巨细的每日更新。突出关键决策与指标拐点。
  2. **障碍要配对策**：绝不只汇报风险或阻塞而不提出至少一条具体的缓解办法。
  3. **WBS 与责任排期**：收尾总结必须给出工作分解结构（WBS），含清晰的里程碑、日期与明确的负责人。

## 3. 12 个企业场景与高管决策严谨性

在企业环境里，演示文稿是给高风险决策者看的。下面这些专门规则适用于 12 个企业运营场景：

### 3.1 高管决策闭环 (`DECISION_ASK_MISSING`)
* **要求**：每一份面向领导的演示（`project_charter`、`annual_strategy_okr`、`team_headcount_review`、`tech_rfc_review`、`cross_team_alignment`）**必须以一项结构化的决策请求收尾**。
* **禁止**：用"谢谢""Q4 持续优化"之类泛泛的总结，或纯资讯性的收尾结束。
* **必备结构**：
  - 方案取舍对比（方案 A / B / C，含优势、短板、成本、风险）。
  - 明确的作者推荐（"我们推荐方案 B……"）。
  - 明确的待批清单（`sign_off_items`），写明领导需要批准什么（编制、预算分配、跨团队人员、里程碑排期）。

### 3.2 严谨的多维对标 (`BENCHMARK_UNBALANCED`)
* **要求**：任何对外部竞品或架构的比较，都必须建立可信的三维坐标系：
  1. **行业标杆**：业界标准或头部玩家做到什么程度。
  2. **直接竞品**：同类替代方案表现如何。
  3. **现状 / 自研基线**：什么都不做的真实成本。
* **禁止**："全绿对全红"的清单——演讲者的方案不带任何取舍，神奇地在每个维度都胜出。
* **必备**：明确写出迁移摩擦、认知学习曲线、运维复杂度与适用场景边界。

### 3.3 晋升归因与 STAR 净贡献 (`PROMOTION_LAUNDRY_LIST`)
* **要求**：在职级晋升评审（`promotion_assessment`）里，候选人必须证明自己带来的净增量业务贡献。
* **禁止**：
  - 罗列日常职责的流水账（"参加了 X 会议，支持了 Y 项目"）。
  - 把宏观环境或团队基线的增长算作个人独有的功劳。
* **必备**：
  - 严格的 **STAR** 因果：问题危机（情境）→ 职责边界（任务）→ 独创的杠杆（行动）→ 剥离后的净收益（结果）。
  - 方法论深度：把一次性的修复沉淀为组织级蓝图、可复用的 SDK 或标准作业程序（SOP）。
  - 下一职级的愿景：面向下一级别的前瞻承诺。

## 4. 自动执行机制（`cli.py audit`）

`ContentAuditor` 与 `SemanticAuditor` 以确定性的方式核验这些红线：

1. **套话扫描**：对 `BUZZWORD_BLACKLIST` 做正则匹配。每次命中都会触发一次结构扣分和一条可执行的发现；自 v3.7 起，发现还带有具体的改写（`suggestion`），例如"闭环"变成"写出闭合的具体环节，如告警、定位、回滚、复核"，"抓手"变成"写出具体动作和负责人"。
2. **行动标题检查**：核验标题是否以结论关键词或主动动词开头，标出"概览""现状"这类被动标题。
3. **核心证据密度**：扫描 `core_evidence` 与页面正文里可核验的数字（`%`、`ms`、`x`、货币、计数）。自 v3.7 起，每个数字还必须说明出处（见第 10、11 条）。
4. **页间转折**：确保转折语属于公认的修辞类别（`contrast`、`causality`、`breakthrough`、`progression`、`evidence`、`action`）。
5. **决策闭环审计（`DECISION_ASK_MISSING`）**：核验面向领导的演示，在收尾页里有明确的方案选项或待批请求。
6. **客观对标审计（`BENCHMARK_UNBALANCED`）**：标出缺少取舍或缺少多维平衡的对比表。
7. **晋升归因审计（`PROMOTION_LAUNDRY_LIST`）**：标出晋升与职业述职里缺少量化业务成果的零散任务流水账。
8. **内容过薄（`THIN_CONTENT_P<n>`，v3.6）**：页面正文（不含页眉）比其版式所需的更短，说明版式在为太少的内容撑场面。补事实或合并这一页。各图元的下限见[场景提纲样例](scenario_outlines.md)。
9. **证据预算（`EVIDENCE_BUDGET_P<n>`，v3.6）**：指标页里带数值的指标不足一半。
10. **无出处的数字（`UNSOURCED_FIGURES_P<n>`，v3.7）**：页面上没有任何 `source` 覆盖的数字。给页面或条目加上 `source`，或标 `status: "todo"`；不要让一个数字看起来像事实。
11. **占位证据（`EVIDENCE_TODO_P<n>`，v3.7）**：标为 `status: "todo"` 的数字。交付前必须换成真实数据（只要还有，`build --final` 就拒绝构建）。`EVIDENCE_ESTIMATE_P<n>` 与 `EVIDENCE_ILLUSTRATIVE_P<n>` 是提示：页脚会把该页标注为"估算"或"示例数据"。
